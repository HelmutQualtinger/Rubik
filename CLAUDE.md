# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single self-contained `index.html` implementing a fully interactive 3x3x3 Rubik's Cube with Three.js (loaded via CDN + import map — no build step, no package.json, no dependencies to install). Open the file directly in a browser to run it.

`social-preview.png` (1200×630, repo root) is the Open Graph / Twitter card image referenced by absolute URL in `index.html`'s `<head>` (`og:image`/`twitter:image`, pointed at the GitHub Pages URL). It's a plain screenshot of the app, not hand-designed — regenerate it by rendering `index.html` at a 1200×630 viewport (2x device scale looks best, then downsample back to 1200×630) after any visual redesign, the same way `screenshot.png` is refreshed for the README. The favicon is a small inline `data:image/svg+xml` in `<link rel="icon">` (an isometric 3-face cube in the app's own U/F/R sticker colors) — no separate icon file.

## Development

- Run: open `index.html` in any modern browser (or `python3 -m http.server` and visit it — needed only if testing module/CORS behavior, plain `file://` works fine here since Three.js is loaded from a CDN import map).
- There is no build, lint, or test tooling in this repo. Verify changes by loading the page and checking the browser console, or by driving it headlessly with Playwright (`chromium.launch()` → `page.goto('file://.../index.html')`) to check for `pageerror`/console errors and take screenshots.
- Three.js version is pinned in the `<script type="importmap">` block (currently `three@0.169.0`, resolved from `unpkg.com`). Bump the version there — and in the `three/addons/` path — together; addon modules (OrbitControls, RectAreaLightUniformsLib, RoomEnvironment) come from the same `examples/jsm/` tree and must stay in lockstep with core.

## Architecture

Everything lives in one `<script type="module">` block at the bottom of `index.html`, structured top to bottom as:

1. **Constants & color table** — `SPACING`/`CUBIE`/`STICKER_INSET` control cubie geometry and gaps; `COLORS` maps face keys (U/D/R/L/F/B) to sticker hex colors; `TURN_MS` (460ms) is the base manual-turn duration — scramble and solve pass their own shorter `duration` per move so mass turning stays brisk.
2. **Audio** (`ensureAudio`, `playClick`, `playSolvedChime`) — every sound is synthesized with the Web Audio API at call time, no audio files. `playClick()` layers a short bandpassed noise burst (the transient) with a decaying low sine (the "thock") and is called once per turn from inside `rotateLayer`, with a small random pitch offset per call for a less mechanical, more organic click train during scramble/solve. `playSolvedChime()` fires a 4-note triangle-wave arpeggio from `onSolved()`. Browsers require an `AudioContext` to be created/resumed from within a genuine user-gesture handler, so `ensureAudio()` is called synchronously at the top of the `pointerdown` listener and every control-button `click` handler — never lazily from inside an animation callback. The `soundEnabled` flag (toggled by `#sound-toggle`) gates both functions.
3. **Renderer/scene/camera/OrbitControls** — standard Three.js boilerplate. A procedural `RoomEnvironment` is baked via `PMREMGenerator` into `scene.environment` specifically so the brushed-metal materials (metalness-heavy, no diffuse response) have something to reflect.
4. **Lighting rig** — a hemisphere light plus `RectAreaLight`s (`boxTop`/`boxBottom`/`sideKick`) positioned above/below/side for soft, diffuse illumination, and one dim `DirectionalLight` kept only to cast a soft ground-contact shadow (`sun`). The `RectAreaLight`s are parented to `camera` (via `camera.attach()`, which preserves their authored world position/aim while reparenting) rather than to `scene`, so they turn rigidly with the view instead of sweeping across the cube's brushed-metal faces as `OrbitControls` orbits the camera — on manual drag or the idle `autoRotate` spin. This requires `camera` itself to be added to `scene` (`scene.add(camera)`), since the renderer only collects lights by traversing the `scene` graph; a light parented to a camera that isn't part of `scene` would never light anything. The ambient hemisphere light and `sun` stay scene-fixed on purpose, so the floor contact-shadow doesn't swing around with the camera.
5. **Materials** — `stickerTexture()`/`brushedTexture()` generate canvas textures at runtime (rounded-rect sticker color, directional brush-noise bump map); `stickerMaterial()` is memoized per color in `stickerMatCache` and `plasticMat` is shared by every cubie body.
6. **Cube data model** (`cubies` array + `buildCube()`): 27 `THREE.Group`s on an integer grid `x,y,z ∈ {-1,0,1}`, each holding one black body mesh plus one sticker `Mesh` per exterior face. Each cubie tracks its logical grid position in `.pos`, independent of its Three.js transform.
7. **Programmatic layer rotation** (`rotateLayer`, `integerRotate`, `snapTransform`) — used by `scramble()` and `solveCube()`, i.e. moves the code decides on itself, always a fixed 0°→±90°. Matching cubies are reparented onto a temporary pivot `Group` via `pivot.attach()` (preserves world transform), the pivot is animated one axis by the full ±90°, then cubies are reparented back with `cubeRoot.attach()` and their `.pos` updated via a hand-rolled integer rotation matrix. Positions/quaternions are snapped to exact grid values afterward to prevent floating-point drift from compounding over many turns. Every completed turn is also pushed onto `history` as `{axis, layerValue, dir}` unless the caller passes `record:false`, and triggers `playClick()`. The live pointer-drag path (point 9) does **not** go through this function — see there for why.
8. **Solve detection** (`checkSolved`): for each of the 6 global faces, finds — per cubie in that layer — whichever sticker's *current world-space normal* points closest to that face's axis (not which sticker was originally assigned there), then checks all 9 are the same color. This makes it orientation-agnostic and correct after arbitrary scrambling. A sticker's world normal is `child.userData.localNormal` (its fixed outward direction *in the cubie's local space*, cached once at build time) rotated by **the cubie group's** current world quaternion — not the sticker mesh's own `getWorldQuaternion()`, which would double-apply the sticker's local rotation and silently never detect a solve. (This was a real bug once; if solve detection ever stops firing, check here first.)
9. **Pointer interaction — live drag-follow turning**: `pointerdown` raycasts against cubie bodies only; if it hits one, `OrbitControls` is disabled and a drag session starts, recording the grabbed face's world-space normal axis/sign and the exact 3D grab point (`drag = {...}`, resolved:false). If `pointerdown` misses all cubies (or `animating` is already true), `OrbitControls` handles it natively for camera orbit. A grabbed face can only turn about the two axes lying in its own plane, so once `pointermove` clears a small pixel threshold, the gesture is resolved **once**: for each of the 2 candidate axes, compute the 3D direction a point at the grab location would move under a small *positive* rotation about that axis (`tangent = axis × normal`, i.e. `v = ω × r`), project that as a 2D screen direction, and score it by `|dot|` against the actual mouse-drag vector — the axis with the higher score wins, and its (signed, not abs'd) screen tangent is kept as `drag.tangentDir`. From then on **every** `pointermove` re-projects the live cumulative drag onto `tangentDir` (`along = dragVec.dot(tangentDir)`) and sets `drag.pivot.rotation[axis]` directly from it — this is what makes the layer visually track the cursor in real time rather than snapping instantly. The pixel-to-radians scale (`pixelsPerQuarterTurn()`) is deliberately *not* derived from the specific grabbed point's own projected 90° arc (points near a rotation axis, or moving mostly toward/away from the camera, would give wildly inconsistent — sometimes near-zero — pixel distances for the same physical turn); instead it's a smooth formula from camera distance, viewport height, and FOV against one fixed representative radius, so it stays consistent across every grab point and zoom level. On `pointerup`, `finishDrag()` tweens the rest of the way to the nearest quarter-turn if `|drag.angle| >= 45°`, or back to the start otherwise (a cancelled drag — no history/move-count/sound), starting from wherever the live angle already was. See the large comment block above the `pointermove` listener for the full derivation.
10. **Scramble/Solve/Reset/stats**: `scramble()` fires a sequence of awaited `rotateLayer` calls in a loop (recorded to `history`, still clicking, but never counted as player moves). `solveCube()` is a pure undo stack: it pops the entire `history` array, reverses it, and replays each move through `rotateLayer` with `dir` negated and `record:false` — no cube-solving algorithm involved, so it always reaches solved regardless of what produced the current state. `buildCube()` is called again wholesale on Reset (which also clears `history`) rather than reversing moves. The **Solve** button (`#btn-solve`) is disabled whenever `history` is empty via `updateSolveButtonState()`. `rotateLayer()` itself only ever handles `history`/`record` bookkeeping — move counter, timer, and `checkSolved()` are exclusively driven from `finishDrag`'s completion block (point 9), since a scramble/solve step is never a player move and a live drag turn doesn't call `rotateLayer` at all.

## Key invariants to preserve when editing

- A cubie's `.pos` (integer grid coordinate) must always be updated *after* its animation finishes and its transform is snapped — never optimistically.
- Any new geometry that needs correct outward-facing normals for `checkSolved()` must have `userData.face` and `userData.localNormal` set the same way `buildCube()`/`patchAllNormals()` do it now, and must be read via the **parent cubie group's** world quaternion, not the sticker mesh's own (see point 8 above).
- **Never compare `Math.abs(x) > Math.abs(bestSoFar)` with `bestSoFar` initialized to `-Infinity`.** `Math.abs(-Infinity)` is `Infinity`, so that comparison is false on every iteration and the "best match" is never selected — the loop silently keeps its initial default forever. This exact bug once made every drag turn ignore direction entirely (always resolved to the same fixed axis and `dir:+1`, no matter which way you dragged) without throwing or looking obviously wrong on a solved cube. If initializing a running best-by-magnitude value at the top of a loop, initialize the *magnitude* variable itself to `-Infinity` and compare `Math.abs(candidate) > bestMagnitude` — do not re-wrap the accumulator in `Math.abs()` on the right-hand side.
- Any programmatic move sequence that should be undoable by the **Solve** button must go through `rotateLayer()` with `record` left at its default (`true`); pass `record:false` only for moves that are themselves undoing history (as `solveCube()` does), or they'll re-enter `history` and corrupt the undo order. Live drag turns record directly inside `finishDrag()` instead.
- After changing anything in `buildCube()`, remember `history` and `moveCount`/timer state are *not* reset automatically — only the Reset button clears them.
- Any new way of triggering a turn (new button, keyboard shortcut, etc.) must call `ensureAudio()` synchronously inside its own user-gesture event handler before anything async happens — calling it later (e.g. inside a `.then()` or `rotateLayer`'s own logic) will leave the `AudioContext` suspended in most browsers and every sound will silently no-op.
- The shared `animating` flag is claimed the moment a drag's axis resolves (not just at `pointerdown`) and released only when `finishDrag()`'s tween completes — it's what stops Scramble/Solve/Reset, or a second drag, from starting mid-turn. If you add a new interaction path, gate it on `animating` the same way rather than adding a separate lock.
